# Install catcher: design (APPROVED by Harsh 9 Oct 2026: option B, Cloudflare Worker; built in services/install-catcher)

**What it is for.** A client store (outside our Shopify organization, reached through collaborator access) installs its own copies of
our three apps. Our blocks show only while the app-data metafield `dtj.licence` on that installation is `active` (fail-closed). To set
it, and to switch it off later (the kill switch), we need a key to that store. The install catcher is the small web service that
receives that key when the client installs, keeps it safely, and flips the licence when Harsh says so. It is the foundation of
part 2 of the main task (the automated licence kill switch).

**Why we need it (verified in Shopify's docs, 9 Oct 2026).** Our licence tool (`tools/licence.py`) uses the client credentials grant,
and "the client credentials grant only works when the app and the store belong to the same Shopify organization ... Client
credentials can't reach a store outside your organization, including a client's store." Collaborator access does not change who
owns the store. For a store outside our organization the docs point to custom distribution plus the authorization code grant.

## The facts the design rests on (shopify.dev, read 9 Oct 2026)
- **Authorization code grant:** send the merchant to `https://{shop}/admin/oauth/authorize` with `client_id`, `redirect_uri` and a
  random `state`; Shopify comes back to `redirect_uri` with `code`, `hmac`, `shop`, `state`, `timestamp`. Check `state`, check the
  `hmac` (remove it, sort the rest, HMAC-SHA256 with the app's client secret, constant-time compare), check `shop` against an anchored
  `^[a-z0-9][a-z0-9-]*\.myshopify\.com$`. Then POST form data `client_id`, `client_secret`, `code`, `expiring=1` to
  `https://{shop}/admin/oauth/access_token`.
- **Expiring offline tokens:** the answer holds an access token (example: 3,600 s) and a **refresh token (90 days)**. "New public
  apps must use expiring offline access tokens"; we use them too, so nothing changes if we go public later. Consequence: we keep the
  refresh token and must use it at least once every 90 days.
- **Managed installation is the default** (`use_legacy_install_flow` false): the scopes in `shopify.app.toml` are granted at install.
  Our copies declare **no scopes** (`scopes = ""`): the client grants us no access to products, orders or customers. The licence is a
  metafield on our own app installation (our tool already writes it with a no-scope token).
- **Custom distribution:** one app copy serves one store. Three copies per client (the 100 KB Liquid cap per app forces three apps).

## How an install works
```
Client clicks the custom-distribution install link (Shopify)          [one per app copy; generated by Harsh in the Dev Dashboard]
  -> Shopify installs the app (managed installation, no scopes)
  -> Shopify opens the app's address (application_url):  GET /start/<app>?shop=..&hmac=..&timestamp=..
       catcher: shop is this app's assigned store? hmac valid? timestamp fresh (< 5 min)?   else: refuse, log, alert
       catcher: make a one-time state (signed, 10 min), redirect to https://<shop>/admin/oauth/authorize?client_id=..&redirect_uri=..&state=..
  -> Shopify sends the merchant back:  GET /callback/<app>?code=..&hmac=..&shop=..&state=..&timestamp=..
       catcher: check state, hmac, shop, timestamp again; exchange the code (expiring=1)
       catcher: metafieldsSet dtj.licence = "active" on currentAppInstallation (the ONLY write it may do)
       catcher: encrypt the refresh token and store it; write an audit row (no token in it)
       catcher: show "DTJ is connected. You can close this tab."
Uninstall: Shopify webhook app/uninstalled -> verify the webhook hmac -> delete that store's token -> audit row
Every 30 days: refresh each token (keeps it alive well inside 90 days); a failure alerts Harsh
Kill switch (part 2): POST /licence {shop, app, state: active|inactive, approved_by} signed with a shared key
       -> refresh -> metafieldsSet -> read back -> audit row. Harsh's Telegram button (n8n) calls this; n8n never sees a store key.
```
Each app copy's `shopify.app.toml` (a per-client file such as `shopify.app.<client>.toml`, so our current apps are untouched):
`embedded = false`, `application_url = https://<catcher>/start/<app>`, `[auth] redirect_urls = [https://<catcher>/callback/<app>]`,
`scopes = ""`, and a webhook subscription `app/uninstalled -> https://<catcher>/webhooks/<app>`.

## Where it runs: three options
| | A. Inside n8n (Hostinger) | B. Cloudflare Worker (recommended) | C. Small Python service on the Hostinger server |
|---|---|---|---|
| Secrets (client secrets, vault key) | n8n code steps cannot read n8n credentials; would need server settings `NODE_FUNCTION_ALLOW_BUILTIN=crypto` (n8n disables module imports by default) and secrets as server environment variables readable by every workflow; **a restart per new client** | Worker secrets (encrypted by Cloudflare, set once per app with `wrangler secret put`), never in code or chat | Server environment / a secrets file on the VPS |
| Token storage | a data table holding ciphertext (needs the crypto setting above) | Cloudflare KV holding AES-GCM ciphertext, key = a Worker secret | SQLite on the VPS, encrypted |
| HTTPS address | yes (n8n webhooks) | yes (`*.workers.dev` or a subdomain) | needs a reverse-proxy route on the server |
| Scheduled refresh | n8n schedule | Worker cron trigger | cron on the server |
| Fits our rule "small tested code services, keep n8n thin" | no: security logic in workflow nodes | yes: one small file of code in git with tests; n8n stays the control panel | yes |
| What Harsh does | change n8n server settings and restart, per client | a free Cloudflare account and one sign-in for the deploy tool | SSH access for us to the VPS |

**Recommendation: B, a Cloudflare Worker.** It keeps every store key away from n8n and from chat, needs no server work, and the code
(one TypeScript file, tests, `wrangler.toml`) lives in git next to the apps. n8n stays the place Harsh presses buttons.

## Safety rules built in
- The only write the catcher can make is `metafieldsSet` for `dtj.licence` on our own app installation (an allowlist, as in
  `licence.py`); with no scopes granted it could not read or change anything else in the store anyway.
- A store key is never logged, printed, returned or sent to n8n. Refresh tokens are stored AES-GCM encrypted; the vault key and the
  client secrets are Worker secrets.
- Each app copy is pinned to its one client store: any other `shop` is refused.
- `hmac`, `state` (one-time, expires in 10 minutes) and `timestamp` (5 minutes) are checked on every Shopify request; webhooks are
  verified with their own HMAC header.
- Licence changes need a signed request and a named approver, and every action writes an audit row (what, store, app, before,
  after, approver, time). Retries: 429/5xx with backoff, max 3; after 3 failures: stop and alert.

## Build plan (after approval)
1. Worker code + tests (hmac, state, shop pinning, token exchange and refresh with a fake Shopify, encryption round trip, the write
   allowlist, webhook verification). Deploy to a test address.
2. Per-client app files for the three copies (`shopify.app.<client>.toml`), linked to the three new apps with
   `shopify app config link --client-id ... --file-name ...`, released with `shopify app deploy --config <client>`.
3. Harsh generates the three install links (custom distribution, the client's `.myshopify.com`) and installs on the client store.
4. Verify: licence reads `active` for all three; a block shows in the draft theme; the kill switch flips one app off and on.
5. Per-client registry for the page builder (each copy has its own block addresses) and the first real page, written to a draft.

## To verify during the build ([VERIFY])
- That managed installation opens `application_url` with `shop` and `hmac` for a non-embedded app, so the catcher can start the
  code flow (if not: set `use_legacy_install_flow = true`, which the docs describe but do not recommend).
- That an authorization with no scopes returns a token that can write our own app-installation metafield (our client-credentials
  token already does).
- Whether refreshing returns a new refresh token each time (store the newest).
- Whether Shopify requires the privacy (compliance) webhooks for custom-distribution apps.
- Cloudflare free-plan limits for Workers, KV and cron (expected well above our volume: a few requests a day).
