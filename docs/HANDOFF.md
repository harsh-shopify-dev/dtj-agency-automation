## MAIN TASK: READ THIS FIRST (Harsh, 9 Oct 2026; every Claude session must follow it before anything else in this file)

**The goal of this whole project is a STORE FACTORY, in two parts. Everything else is support.**

1. **AI builds the client's store pages with OUR blocks.** Once our apps are installed on a client's store, an automation that uses the **Claude API (with an API key)** takes the client's brand and product facts and designs the pages from our blocks and sections: it **adapts to the client's brand** (colour palette, fonts, shape language, tone) and follows **high-converting conversion-agency structure** (the kind of product pages agencies such as ConversionWise build), instead of one fixed template. The hand-built TOILOVA page is the quality bar and the first example; the automation must reproduce that judgment every time, for any brand. A person approves before anything reaches a store.
2. **The licence kill switch, fully automated.** A hosted service holds the client secrets and runs the commands; Harsh controls it from Telegram (or another channel) with **no terminal and no secret ever typed**.

**What is NOT the main task:** n8n workflows for alerts, heartbeats, lead-audit intake, reports, ad guard or billing. They are supporting parts and are built only when they serve part 1 or part 2. #### 1.2 How the kill switch works now
1. Every block starts with `{% render 'dtj-licence', value: app.metafields.dtj.licence.value, ... %}` (generated; see `snippets/dtj-licence.liquid`). The value is an **app-data metafield** `dtj.licence`, stored on the **app installation** (per app, per store). `active` shows the block; anything else, including a fresh install with no value, **shows nothing** (fail closed). In the theme editor an inactive block shows "flag seen: inactive".
2. Writing the flag needs an access token for that store and app. `services/block-library/tools/licence.py` gets one with the **client credentials grant** (client id from `shopify.app.toml`, secret from an environment variable), then reads/sets the metafield with `metafieldsSet` (the only mutation it may send). Every change needs `--approved-by` and appends a row to `.work/out/licence-log.jsonl`.
3. Harsh's terminal flow: `services/block-library/tools/dtj-licence.cmd|.ps1` (`hide`, `show`, `status`, `-App`, `-DryRun`) asks for each app's secret hidden. `licence.py --app all` loops the three apps.
4. Proven on 8 Oct 2026: flag flips work on the test store for all three apps (Harsh ran them).

### 4. Target architecture

```
 Harsh (Telegram)                     Billing events (Razorpay/Stripe/invoice tool)  [shadow first]
        |  webhook (secret-token header)             |  signed webhook
        v                                            v
```

Components
1. **Licence service** (Python, matches the repo; reuse `licence.py` logic as a library, do not rewrite it). Hosting candidates: Fly.io, Render or Cloud Run (needs always-on HTTPS for webhooks). Decide in D5.
2. **App registry** (config, no secrets): the three apps with handle, client id (from each `shopify.app.toml`), secret reference name, API version pin (currently `2026-07` in `licence.py`).
3. **Token vault**: table `installs(shop, app_key, token_ciphertext, scopes, installed_at, status, last_verified_at)`; encrypt with a key from the secret manager (AES-GCM, key id stored). For own-org test stores the service can mint short-lived tokens with client credentials instead of storing them.
4. **Policy engine**: pure code, no AI. Decides whether an action runs now, needs a confirm tap, or is refused. Reads `AUTOMATION_ENABLED`, per-store flags, caps (e.g. max N changes per hour), protected stores, allow-list.
5. **Executor + verifier**: sets the metafield, then reads it back with a second call and compares. Retries on 429/5xx with backoff (max 3), refresh token once on 401, then stop and alert (RUNBOOK 6).
6. **Audit log**: append-only table (+ daily export to BigQuery/GCS once Phase 0 data layer exists). Every row has `run_id`, actor, store, app, before, after, result, evidence.
7. **Telegram bot**: webhook mode, validates the `X-Telegram-Bot-Api-Secret-Token` header, replies in plain language. No secret ever appears in a message.
8. **n8n** (already part of the plan, RUNBOOK 2.1): thin glue only (scheduled heartbeat, billing webhook relay). The kill logic lives in the service, not in n8n workflow JSON.

### 6. Security design (summary)
- Secrets: a managed secret store (GCP Secret Manager, Doppler or the host's encrypted secrets). Never in git, `.env` committed files, logs, Telegram, screenshots. A repo secret scanner in CI (gitleaks) blocks pushes that contain `shpss_`, `shpat_`, bot tokens.
- Least privilege: the app's own scopes only; no delete scopes; the executor can call **only** `currentAppInstallation` reads and `metafieldsSet` on key `dtj.licence` (allowlist enforced in code, as `licence.py` already does).
- Telegram: webhook secret token, user-id allow-list, confirm buttons with nonce and expiry, per-user rate limit, message size limit, no logging of message bodies beyond the command.
- Shopify webhooks: verify HMAC and timestamp, validate JSON against `schemas/`, idempotency key, dead-letter queue for anything malformed (RUNBOOK 7).
- Rotation: documented procedure per secret (rotate in Dev Dashboard, update secret store, restart, run `/status` all). The leaked DTJ Sections secret is the first rehearsal.
- Fail direction: licence absent or unreadable = block hidden (already so in Liquid). The service being down never changes storefronts by itself.
- Unattended AI: none in the kill path. The switch is deterministic code. AI (Claude API with a key) only assists around it (summaries, anomaly notes) with spend caps.
- Compliance: the service stores store domains and tokens, not shopper data. **[VERIFY]** whether Shopify's mandatory privacy webhooks apply to our distribution type and implement if so.

## 8. The block library (the app) in detail

**How a block is made:** `manifests/<id>.json` (settings, content slots, standard controls, `test.sample/expect`, `script`, `css_includes`) + `src/<id>.liquid` (body only) + `src/<id>.css` (+ `src/<id>.js`). `python tools/build_blocks.py` writes `extensions/dtj-blocks/blocks/dtj-<id>.liquid` (prelude + body wrapped in the licence gate + **compact** `{% schema %}`) and `assets/dtj-<id>.css|.js`. **Never edit generated files.** Standard controls added to every block: spacing (padding 4 sides + top/bottom margin), alignment, text/background colour, corner radius, text size (per manifest). Colours default empty (follow the theme); no default copy.

**Licence gate:** `snippets/dtj-licence.liquid` is a WRAPPER: `{% render 'dtj-licence', value: app.metafields.dtj.licence.value, content: ..., design_mode: request.design_mode, attributes: block.shopify_attributes %}`; prints the content only when the flag is exactly `active`; otherwise nothing on the storefront (no markup shipped, not even in comments) and, in the theme editor only, a dashed note "DTJ block hidden: the licence is not active (flag seen: ...)". **Keep that diagnostic in every block** (it found a bug in one screenshot).

**Current blocks (release `dtj-blocks-13`, 71.8 KB of 100 KB, 7 of 30 blocks):**
| id (file `dtj-<id>`) | Editor name | What it is / non-obvious behaviour |
|---|---|---|
| `hero-points` | DTJ Hero Points | eyebrow pill + subheading + benefits typed one per line (max 8 non-blank); ticks use the shared disc+tick icon |
| `rotating-text` | DTJ Rotating Text | typewriter, up to 6 phrases + prefix; script `dtj-rotating-text`; reduced-motion safe |
| `social-proof` | DTJ Social Proof Line | stars from the real review-app rating (`product.metafields.reviews.rating`), manual rating only as fallback; stock line only when inventory is tracked and qty>0 with Harsh's own text (`{count}`); two own lines |
| `testimonials` | DTJ Testimonials | up to 5 reviews, avatar/photo, stars default none, badge = free text, auto-advance + swipe, pause on hover/off-screen |
| `shoppable-reels` | DTJ Shoppable Reels | 6 cards image or video, **one `product_list`**: card N links to product N; muted autoplay when 60% visible, tap for sound; translatable play/pause labels |
| `shade-picker` | **DTJ Option Picker** | up to 8 sibling PRODUCTS as swatches/pills, **one `product_list`**: option N = product N; current product auto-highlighted by handle; sold-out dimmed and unclickable; hover shows the name beside the label |
| `addons` | DTJ Add-ons | **one `product_list`**: first four = add-on cards, `s{i}_alt` picks a list position 5-8 as a swap; real prices/compare-at only; live total from the chosen variant; ticked add-ons + product go in ONE `/cart/add.js` (add-to-cart and buy-now clicks intercepted in capture phase; nothing ticked = theme flow untouched; failure falls back to the theme form); after-add default = cart page (drawer is best effort) |

**Library rules enforced by `tools/check_library.py` (each one came from a real failure, section 11):** manifest valid and every slot exists in the schema; no default copy on text-like settings and no colour defaults; every block runs the licence gate (wrapper) and its snippets exist; no hard-coded hex colours (ignores `&#9733;`-style codes); range default on a step, <=101 steps, select default is an option, **range `unit` never blank**; snippets never read `block.`/`section.` (pass values in); **never capture or compare a snippet's output**; **max 6 header/paragraph settings**; **every `<img>` needs an explicit size in the block's CSS**; **no `{`/`}` inside a `{{ ... }}` output** (put literals in `{% assign %}`); **scripts < 10,000 bytes**; **schema name <= 25 characters**; **at most ONE resource picker per type** (`product`, `product_list`, `collection`...: enforced by Shopify for `product`, assumed for the rest); **never read a `*_list` setting by position (`list[0]`): loop over it** (rule 18, 6 Oct 2026); Liquid budget (printed): 100 KB per app, 30 blocks.

**App-block limits learned (Shopify server, not documented in one place):** 100 KB of Liquid per extension (one extension per app); 30 blocks; no child blocks; <=6 non-interactive settings; 1 picker per resource type; name <= 25 chars; blank range unit rejected; `{`/`}` inside output tags rejected; Theme Check errors on scripts >= 10,000 bytes and warns above 40 settings (advisory; four blocks have 41-54).

## 10. Lessons (how to work on this)

1. **Server-side validation is stricter than every local check.** Each new block family so far was refused at least once at `shopify app deploy` (6-header cap, `{count}`, blank unit, 1 product picker, 25-char name, ...). Budget a retry per new family; after each refusal add a rule to `check_library.py` with a test, then retry the same approved deploy. Shopify's Theme Check did NOT catch most of them.
2. **The local Liquid engine (python-liquid) is not Shopify.** Known differences: `nil != blank` (Shopify: nil == blank; the test harness models unset settings as `""`), `<=`/`>=` exclude equality for computed decimals (use strict `<` with +1), no `json`/`image_url`/`money`/`video_tag`/`payment_type_img_url` filters (stubbed in `tests/test_generated_blocks.py`). Tests wrap every snippet in `<!-- BEGIN app snippet -->` comments like the real editor.
3. **Put raw-value diagnostics in the editor-only note** ("flag seen: ..."): one screenshot found a bug that three theories missed.
4. **Verify after every store write** by reading it back (pull the file, list themes, query the product) and ask Harsh to open the editor: a push can break the editor preview without any CLI error.
5. **Theme CSS fights blocks:** Horizon stretches images and styles buttons. Size images in CSS, not only in tags; wrap long text; never rely on tag attributes.
6. **Mutation-test the tests:** deliberately break the gate and confirm the tests fail.
7. **Write files with the file tools**, not long shell heredocs with embedded escapes (see errors 5-6).
8. Never claim a visual/behavioural result you cannot see. Say "not verified" and say what Harsh should check.
